# gRPC: a second transport, not a second implementation

_Added 2026-09-25, against `docs/project_status.md` item d ("gRPC audio
stream + Python SDK")._

## Why this is safe to trust

Every route in `voiceguard.serve.app` (REST/WS) and every RPC in
`voiceguard.serve.grpc_service` (gRPC) calls the same
[`build_session_stack`](../src/voiceguard/serve/session.py) and drives the
same `SessionManager` -- the scorer, the speaker verifier, the prosody
model, the fusion/policy logic and the audit log are constructed exactly
once, in one place, regardless of which transport a caller uses. Nothing
about the decision engine is reimplemented for gRPC; only the encoding and
the wire protocol differ. `tests/test_grpc.py::test_rest_and_grpc_agree_on_the_same_clip`
sends the identical clip through both transports and asserts they land on
the identical action and fused score -- not "close," identical.

## Surface

`src/voiceguard/serve/proto/voiceguard.proto` mirrors the REST session API
1:1:

| RPC | REST/WS equivalent |
|---|---|
| `CreateSession` | `POST /api/session` |
| `UpdateContext` | `POST /api/session/{sid}/context` |
| `Enroll` | `POST /api/session/{sid}/enroll` |
| `Analyze` | `POST /api/session/{sid}/analyze` |
| `Acknowledge` | `POST /api/session/{sid}/acknowledge` |
| `GetAudit` | `GET /api/session/{sid}/audit` |
| `StreamAudio` (bidi streaming) | `WS /api/session/{sid}/stream` |

The raw (non-session) detector path -- `/api/score`, `/api/stream` -- is
REST/WS only. It is the "it's real-time" proof for the demo, not a product
surface; gRPC parity for it was not built, to keep this addition scoped to
the actual deliverable (the session API).

## Run it

```bash
pip install -e ".[dl,serve,prosody,grpc]"
python scripts/serve_grpc.py                       # localhost:50051
python examples/grpc_client.py enrol.wav benign.wav cloned.wav
```

`examples/grpc_client.py` is the gRPC counterpart to `examples/rest_client.py`
-- same flow, same printed output, different transport. Run both against
the same clips and diff the output if you want to see the parity for
yourself.

## Provenance is carried over too

`AuditEvent` (the gRPC message) has the same `model` / `front_end` /
`git_commit` fields as the REST audit JSON -- the provenance-stamping
discipline this project applies everywhere else
(`docs/evaluation_protocol.md`) is not REST-only.

## A proto3 default-value trap, fixed here

`CreateSessionRequest.caller_known` is declared `optional bool`, not a
plain `bool`. A plain proto3 `bool`'s unset wire value is `false`, which
does not distinguish "the client explicitly said false" from "the client
didn't set this field, use the server default (`true`, matching the REST
route's `body.get("caller_known", True)`)" -- a client that omits the field
would have silently gotten `caller_known=False`. Caught by
`tests/test_grpc.py::test_session_lifecycle_and_audit` before this shipped
(a context-risk assertion failed because the first analysed clip carried
non-zero context risk when it should have carried none). `amount` and
`channel` don't have this problem: `amount`'s proto3 zero-value (`0.0`)
already matches the intended default, and `channel`'s empty-string case is
handled explicitly in the servicer (`request.channel or "pstn"`), the same
way REST's own `_ctx_out` path handles it.

## Generated code

`src/voiceguard/serve/proto/voiceguard_pb2*.py` are generated by
`grpc_tools.protoc` -- see the regeneration command and the one required
post-generation fixup (a relative import) in `proto/__init__.py`. Excluded
from ruff (`pyproject.toml`'s `extend-exclude`), same treatment as the
vendored reference implementations elsewhere in this repo.

## What this is *not*

- Not a hardened, authenticated, TLS-terminated service -- `add_insecure_port`,
  bind to localhost, same posture as the REST demo server
  (`voiceguard/serve/__init__.py`'s own docstring). Auth/TLS is part of
  `docs/project_status.md` item j (release hardening), not this item.
- Not a published/installable SDK package. `examples/grpc_client.py` is a
  thin, direct usage example -- generated stubs plus ~15 lines of client
  code -- matching the bar `examples/rest_client.py` already set for the
  REST "SDK," not a separately versioned package with its own retry/auth
  conventions.
